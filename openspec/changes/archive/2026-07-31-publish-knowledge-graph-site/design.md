## Context

`.ua/knowledge-graph.json` is tracked in git — 1,096 nodes and 2,885 edges over
264 files, organised into 10 architectural layers and a 14-step guided tour. It
is generated by the Understand-Anything plugin, which is a Claude Code plugin
rather than a repository dependency; it is not vendored here and nothing in
this repository builds it.

Reading the graph required installing that plugin, running `pnpm install`
against its dashboard package, compiling `@understand-anything/core`, starting
a Vite dev server, and opening a one-time tokenised URL printed to the
terminal. The plugin ships a shortcut — it tries to fetch a prebuilt viewer
from the upstream GitHub release before falling back to a local build — but the
installed version (2.9.4) has no upstream tag and no release asset, so that
fetch 404s on every invocation.

The dashboard turned out to already support static hosting. `vite.config.demo.ts`
builds with `VITE_DEMO_MODE=true`, and `App.tsx` under that flag returns
`<Dashboard accessToken="__demo__" />` before the token gate is ever reached,
and resolves data files against `import.meta.env.BASE_URL` instead of a
token-guarded dev-server route. Static hosting is a designed-for path, not a
workaround — which is what made this change small.

## Goals / Non-Goals

**Goals:**
- The graph is readable from a link, with no checkout, no toolchain, and no
  credential.
- Publishing is automatic once a regenerated graph is committed, so the
  maintainer's only action is the regeneration they were already doing.
- A graph that has silently lost structure does not reach the site.

**Non-Goals:**
- Regenerating the graph in CI. See the first decision below.
- Publishing the domain graph, diff overlay, or staleness report. All are
  optional and demo mode skips them entirely.
- A custom domain, or vendoring the dashboard source into this repository.

## Decisions

### Regeneration stays manual; only publication is automated

The obvious reading of "keep the site current" is to regenerate the graph in
CI. Rejected, and the reasons are worth recording because the idea will recur.

Generation is model-driven: non-deterministic, tens of minutes, and metered API
spend. Automating it would put a billable credential in CI, produce a large
unreviewable diff of rewritten prose on every run, and — because the
regeneration job writes `.ua/` while a `.ua/` change is what triggers
publication — create a trigger cycle needing explicit breaking.

Publishing, by contrast, is cheap, deterministic, and credential-free. Splitting
them means the automated half has none of those properties. The maintainer
regenerates deliberately; committing the result is the entire publishing
action.

A middle option was considered and set aside: gate CI regeneration on the
plugin's own deterministic structural fingerprints (`classifyUpdate` returns
`SKIP` when every change is cosmetic), so only structural pushes cost money.
That works and remains available if regeneration is ever automated, but it
solves a problem this change does not have.

### The dashboard is pinned by commit SHA, not by tag

Version 2.9.4 has no upstream git tag and no release asset — the same fact that
breaks the plugin's prebuilt-viewer shortcut. A tag reference would not merely
be weaker than a SHA here; for some versions it does not resolve at all. This
matches the SHA pinning `CMakeLists.txt` already applies to JUCE and Catch2.

The cost is that `dependabot.yml` does not track a raw commit-pinned checkout
of another repository, so the pin advances only when someone bumps it
deliberately. That is the same trade-off already accepted for JUCE and Catch2.

### Verification is a Node script, run before any build work

The gates need git history, JSON parsing, and comparison against a previous
revision. Node rather than Python because the job already provisions Node for
the Vite build, and because this repository's Python toolchain was an open
question at the time (see the `adopt-uv-for-python` change). Running it first
means a bad graph costs seconds rather than a completed build and a failed
publish.

### Regression detection compares against the previously published graph

This is the decision least likely to be guessed from the requirements, and the
one that came from observed failure rather than reasoning.

The analysis pipeline reports edge removals as routine corrections. During the
regeneration that preceded this change, two separate classes of edge were lost
silently: every C++ `tested_by` edge (52 → 5), because the merge script's
test-name patterns recognise a `Tests` suffix for Java, Kotlin, C#, and Scala
but not `.cpp`; and all 16 `defines_schema` edges, because incremental pruning
drops edges asserted by unchanged files that point into re-analyzed ones, with
nothing to re-emit them. Both produced a graph that loaded cleanly and passed
the pipeline's own validation with zero issues.

So correctness against a schema is not enough — the check has to be
differential. Comparing per-type edge counts against the previous revision is
what separates cleanup from damage. The threshold (a type disappearing, or
halving) is deliberately coarse: regeneration legitimately moves counts around,
and the cost of a false positive is one maintainer override, while the cost of
a false negative is a silently degraded published graph.

The comparison resolves the previous revision from the file's own git history
rather than `HEAD~1`, so it compares against the last graph actually published
rather than whatever unrelated commit happens to precede it.

### Deployment credentials are scoped to a separate job

The build job runs third-party dashboard source and a downloaded scanner
binary. `pages: write` and `id-token: write` live only on the deploy job, which
runs no repository or third-party code beyond the deploy action itself.

## Risks / Trade-offs

- **The published graph will usually lag the code.** Regeneration is manual, so
  the site describes whatever commit was last analyzed. Mitigated by making the
  lag visible rather than eliminating it: the provenance check warns, and the
  site reports the graph's commit rather than the deployed one. Accepted —
  honest staleness beats silent staleness.
- **The regression gate can block a legitimate change.** A deliberate scope
  reduction — tightening `.understandignore`, deleting a subsystem — looks
  exactly like damage in the counts. Mitigated by a `workflow_dispatch`
  override scoped to the regression check alone, so overriding it does not
  weaken provenance, excluded-path, or secret checks.
- **The excluded-path check is conservative.** It reads only literal directory
  and file patterns from `.understandignore`, skipping negations and character
  classes rather than half-implementing gitignore semantics. A missed exclusion
  is still caught by the gitleaks scan; a wrongly-inferred one would block a
  legitimate deploy, which is the worse failure.
- **Upstream layout is not contractual.** The dashboard lives at
  `understand-anything-plugin/packages/dashboard` in the upstream repository,
  which differs from the layout of the installed plugin. A pin bump could move
  it. The SHA pin means this can only break deliberately, and it breaks loudly
  at build time.

## Migration Plan

Enabling GitHub Pages with the GitHub Actions source is a repository-admin
action that the workflow cannot perform for itself; every deployment fails
until it is done. There is nothing else to migrate — no existing site, no URL
to preserve, and no consumer of the graph other than the local dashboard, which
is unaffected.

## Resolved Questions

- **Does demo mode really bypass the token gate?** Yes. Verified by building
  the bundle and serving it with a plain `python3 -m http.server`: the entry
  page, the JavaScript bundle, and the 1.3 MB graph all returned 200 with no
  token, and the graph arrived intact.
- **Does the build work against upstream, or only against the local plugin
  cache?** Only verified against upstream after the fact — and it did not, at
  first. The upstream repository nests the dashboard one level deeper than the
  installed plugin does, so the first build path was wrong. Corrected and
  re-verified against the pinned commit.
- **Is a `pyproject.toml` or dependency manifest needed?** No. The verification
  script is Node, and the dashboard build uses upstream's own pnpm workspace.
